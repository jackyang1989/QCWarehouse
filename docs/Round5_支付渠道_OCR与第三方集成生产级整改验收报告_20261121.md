## 3. 第三方集成中心与 AES-256-GCM 凭证金库

- **共用加密原语提取**：[`crypto.ts`](../packages/core/crypto.ts) 提取并统一 [`auth.ts`](../packages/core/auth.ts) 中的 AES-256-GCM 加密 `seal()` 与解密 `unseal()`，使用服务端 `SESSION_SECRET` / 独立密钥材料派生密钥。
- **凭证金库与严格脱敏**：[`integrations-admin.ts`](../packages/core/integrations-admin.ts) 维护 `integration_secrets` 表与版本号递增（轮换 `key_version`、`revoked_at` 吊销、前缀掩码 `masked_hint`）。接口与历史事件仅返回脱敏摘要，禁止向 `config` JSONB 注入明文密钥或回传真实秘钥；`integration_events` 记录所有配置变更、轮换、吊销、实测连接与错误摘要。
- **SSRF 防护**：`assertSafeExternalUrl()`（经单元测试 `P10` 验证）阻断内网回环（含 `127.0.0.1`、`::1`、`0.0.0.0`、IPv6 内嵌 IPv4 `::ffff:127.0.0.1`、尾点域名 `localhost.`、非字符串入参及非法协议），仅允许白名单安全外部端点。
- **静态校验 vs 真实连接测试严格分离**：`POST /api/v1/staff/admin/integrations/:key/validate` 仅验证参数结构、环境前缀与必需凭证是否在库；`POST /api/v1/staff/admin/integrations/:key/test` 则强制执行真实本地探针或外网连通测试（Stripe / PaddleOCR `--health` / Google Vision / Webhook 等），无真实凭证绝不伪造 `"healthy"`。

## 4. 多渠道支付编排、PayPal 人工发票与双人 SoD 闭环

- **核心模块**：[`payments.ts`](../packages/core/payments.ts)、[`payment-providers.ts`](../packages/core/payment-providers.ts)、[`integrations.ts`](../packages/core/integrations.ts)、[`admin-reads.ts`](../packages/core/admin-reads.ts)、[`reads.ts`](../packages/core/reads.ts)。
- **渠道动态可用性与切渠安全**：
  - `GET /api/v1/me/payment-channels?charge_id=...` 返回经合规门禁、启用状态与活跃尝试过滤后的真实可付渠道列表。
  - 客户可在未生成待核销凭证前在 Stripe 与 PayPal 人工账单间自由切换：`attempt()` 与 `requestPaypalManualInvoice()` 会在开启新渠道前自动作废无实收记录的旧 `requires_payment` 记录，同时满足唯一索引 `one_open_attempt` 并在存在 `processing` 或已提交人工转账单（`MANUAL_RECEIPT_PENDING`）时准确拦截 `409`。
- **PayPal 人工账单 4 步可审计流程**：
  1. 客户请求开票（`POST /api/v1/charges/:id/paypal-invoice`）：幂等生成 `payments(provider='paypal_manual', manual_state='requested')`，绝不提前激活订单。
  2. 客户提交已转账说明（`POST /api/v1/me/payments/:id/report-paypal-paid`）：支持填写交易号、备注及凭证图片/PDF；仅记录 `customer_reported_at`，绝不推进订单状态。
  3. 财务开票与录入实收（`POST /api/v1/staff/finance/paypal-invoices/:id/issue` & `/record-receipt`，需 15 分钟内 MFA）：强校唯一 `external_transaction_id`（大写规范化 + 局部唯一索引防跨单重用）、计算 `net_amount_cents` 并自动识别 `underpaid` / `overpaid` 状态。
  4. 双人职责分离（SoD）独立核销激活（`POST /api/v1/staff/finance/paypal-invoices/:id/verify`，需 MFA）：数据库 CHECK 约束 `payments_manual_verify_sod` + 服务层双重校验 `verified_by !== recorded_by`（同人核销返回 `403 SOD_VERIFICATION_FORBIDDEN`）；少付（`underpaid`）禁止激活；超付（`overpaid`）须显式传入 `accept_overpayment: true`；核销通过后写入 `payment_events` / `payment_settlements` 并调用权威激活入口 `applyPayment()` 推动订单至 `awaiting_samples`。
- **驳回、取消与人工退款**：支持核销驳回（清除原记录重入队列、留存 `rejected_history`）、发票作废，以及针对非 Stripe 渠道退款单在 Worker [`payments.ts`](../packages/core/payments.ts) 跳过 Stripe API 调用并由财务通过 `POST /api/v1/staff/finance/refunds/:id/execute-manual` 完成凭证归档与 `syncPaymentRefundState()`。

## 5. 自建 PaddleOCR、PDF 证据支持与备选识别链路

- **Python 本地推理引擎**：[`scripts/ocr_engine.py`](../scripts/ocr_engine.py) 基于当前环境已安装的 `rapidocr-onnxruntime`（PP-OCRv4 ONNX 中英文识别）、`pypdfium2` 与 `pypdf`。
  - 支持 `--health` 离线自检；支持 PNG/JPEG/WEBP 与最多 10 页的原生文字 PDF / 扫描图片 PDF。
  - 按 `min(2.0, 2400 / max(width, height))` 控制渲染像素上限，防止高分辨率 PDF 内存膨胀；显式拒绝损坏及加密 PDF（返回真实错误码，不吞错）。
- **媒体安全边界扩展**：[`media.ts`](../packages/core/media.ts)、[`intake.ts`](../packages/core/intake.ts) 与 [`ui.tsx`](../app/ui.tsx) 仅对 `kind='attachment'` 放开 `application/pdf` 上传（`intake_outer` 等仓库现场照类型仍严格限制图片），强制执行魔数与 `pdf-lib` 结构校验。
- **两阶段流水线与结构化解析**：[`ocr.ts`](../packages/core/ocr.ts) + [`ocr-parser.ts`](../packages/core/ocr-parser.ts)：
  - **Stage 1（文字提取 + 坐标块）**：主用本地 `paddle_ocr`（`runPaddleOcr`），支持配置开启 Google Vision `DOCUMENT_TEXT_DETECTION`（Header `X-goog-api-key` 传参 + PDF 先转/前置校验）作为备选增强通道；管理员 `test-extract` 显式指定渠道时不跨渠道静默伪造降级。
  - **Stage 2（采购单结构化抽取）**：识别 1688 / 淘宝 / 微店 / 得物 / 装箱单等多平台单据，处理 PP-OCRv4 粘连字符切分，产出带置信度、低置信度预警及 `bbox` 边界框的候选项。
- **生产健壮性与多租户隔离**：按组织日配额限制（超出返回 `429 OCR_QUOTA_EXCEEDED`）、文件 SHA-256 跨作业去重复用结果、严格基于 `org_id` 隔离 OCR 作业与媒体读取/编辑/拆合/确认、异步 Outbox Worker 事件 `ocr.extract`（[`worker.ts`](../packages/core/worker.ts)）、以及 `cleanupExpiredOcrJobs` 对测试作业清理与超期原始文本脱敏。

## 7. 独立安全与架构审计发现及修复记录（2 P0 + 4 P1 + 5 P2 全部闭环）

Independent read-only security & production audit 提出 11 项缺陷，已全部于代码级修复并经测试复验：
1. **P0-1 · Google Cloud Vision API Key URL 泄露风险**：改用 HTTP Request Header `X-goog-api-key` 传密，不在 URL Query 中拼接密钥。
2. **P0-2 · PayPal 人工队列 SQL 字段错误**：修正 [`payment-providers.ts`](../packages/core/payment-providers.ts) `listPaypalManualQueue()` 中关联 `dispatch_batch_items` 的错误表/字段连接，确保 `GET /staff/finance/paypal-invoices` 稳定返回 200（`P15` 已覆盖）。
3. **P1-1 · Stripe Checkout 复用非 Stripe 待付记录 & 切换渠道唯一索引冲突**：[`payments.ts`](../packages/core/payments.ts) `attempt()` 严格按 `provider='stripe'` 查重；并在客户切渠时安全作废无实收记录的旧 `requires_payment` 记录（同时对 `processing` 与待核销人工收款保持 `409` 拦截），与 `one_open_attempt` 局部唯一索引完全兼容。
4. **P1-2 · Stripe 运行态环境配置混淆**：[`integrations.ts`](../packages/core/integrations.ts) `stripeSettingsFromDb()` 接收 `Pick<DB, "query">`，明确区分环境变量 Sandbox 与数据库受控 Live 状态（`dbGoverned`）。
5. **P1-3 · Google Vision 不支持直接传扫描 PDF**：`ocr.ts` 在调用 Google Vision 前对 PDF 执行拒绝/前置限制并在多页 PDF 路由至 PaddleOCR/pypdfium2。
6. **P1-4 · 渠道不可用时未服务端拦截**：在 `POST /charges/:id/checkout` 入口接入 `assertStripeCheckoutAllowed()`（`P06` 实证拦截关闭后的 Stripe 结账请求）。
7. **P2-1 · 管理员显式指定单引擎测试降级误导**：`adminTestOcrExtract()` 在显式指定 `provider_key` 失败时直接报错，不静默回退到另一引擎（`O15` 已验证）。
8. **P2-2 · OCR 作业重试权限与状态盲区**：`retryOcrJob()` 校验终态、组织日配额并防止覆盖已确认候选项。
9. **P2-3 · SSRF 校验边界绕过**：`assertSafeExternalUrl()` 增加尾点域名、IPv6 内嵌 IPv4 及非字符串防御（`P10` 已验证）。
10. **P2-4 · 财务读取 PayPal 凭证附件授权不足**：[`media.ts`](../packages/core/media.ts) 补全 `paymentProofAttachment` 读取校验，允许 `finance`/`super_admin` 审阅收款凭证同时保持跨租户客户隔离。
11. **P2-5 · PayPal 外部交易流水号大小写重复绕过**：统一转大写归一化并于 `recordPaypalManualReceipt` 前后由 DB 局部唯一索引拦阻同号重入（`P15` 已验证）。
