## 11.3 问题清单（按 P0 / P1 / P2 / P3 分类）

### P0 级（阻断核心业务闭环、跨角色权限断裂、数据口径冲突、生产合规风险）

1. **[P0-01] 质检任务跨端查看 `403 insufficient role` 权限断裂**
   - **现象**：`super_admin` 与 `support` 在 `/admin/inspections` 或 `/admin/orders/:no` 点击质检任务链接跳转到 `/wh/task/:id` 时，后端 `taskDetail` 抛出 `403 insufficient role`；`support` 查看 `/staff/reports/:id` 也抛出 `403`。
   - **根因**：`packages/core/inspection.ts` 仅将 `taskDetail` 授权给 `inspector / reviewer / warehouse_admin`，且缺少管理后台专用的只读/复核监督视图。
   - **修复**：新增 `/admin/inspections/tasks/:id`（`GET /staff/admin/inspections/tasks/:id`）全链路质检监督工作台，并在 `packages/core/inspection.ts` 为 `super_admin` 和 `support` 开放 `taskDetail`、`checkTaskCompleteness`、`staffReport` 的只读查询权限，严格保持写操作职责分离。
2. **[P0-02] 运营总览卡片数字与点击进入的目标队列不一致**
   - **现象**：`/admin` 总览卡片统计 `NOT is_test_order`（正式单 5 笔），点击进入 `/admin/orders` 时默认展示含测试单全量（127 笔），导致卡片显示 `等待收样 0`，点进去却有 `92` 笔。
   - **根因**：`overviewMetrics` 仅计算正式单口径，且卡片链接未传递 `test=production` 参数。
   - **修复**：`overviewMetrics` 返回正式单与全量双口径数据；`/admin` 新增 `仅正式单 (5)` / `含测试单全量 (127)` 切换器，卡片链接显式携带 `?test=production` 或 `?test=all`。
3. **[P0-03] 实物生命周期状态显示 `outbound / pending` 与 `disposed / pending` 语义自相矛盾**
   - **现象**：实物 `S-F53EFBDD`（已退回出库）和 `DSP-E1BB0631`（已双人销毁处置）在界面同时显示 `已出库 / 待核身` 或 `已处置 / 待核身`。
   - **根因**：未绑单无主退回件与逾期处置件不经过订单行 SKU 核身（`identity_state` 保持初始 `pending`），直接渲染 `IDENTITY_STATE_ZH["pending"]` 产生业务误导。
   - **修复**：在 `app/admin-labels.tsx` 实现 `describeWarehouseItemLifecycle` 与 `WarehouseItemLifecycleTags`，结合 `custody_state`、`identity_state` 与 `order_id` 输出准确业务语义（`逾期/无主直接处置（免 SKU 核身）` / `未绑单原样退回/出库（免 SKU 核身）`）。
4. **[P0-04] 生效法务协议包含 `"Development fixture..."` 却无任何风险提示或正文预览**
   - **现象**：`privacy`、`report_notice`、`restricted_items` 的当前生效版本 `demo-v1` 正文均为开发夹具占位文本，`/admin/legal` 仅展示 `active` 绿标。
   - **根因**：缺少正文内容合规扫描与预览工作台。
   - **修复**：后端 `adminDesk` 自动扫描并标记 `is_demo_fixture` 与 `consent_count`；前端 `/admin/legal` 置顶展示红色 P0 合规告警横幅、行内红色风险标签与底部全宽 Markdown 正文预览工作台。
5. **[P0-05] 库存事故高额赔付结案缺少打款凭证强校验**

## 11.8 数据一致性与异常数据核查报告（指令 §8 八大质疑点逐项核实）

针对指令第八节提出的 8 项具体数据与状态质疑，本轮逐一深入 PostgreSQL 数据库与业务服务层进行了取证与修复：

1. **质疑点 8.1：`QW-63A714CB655E` 申报 50 件、3 个包裹，实收 48 件，但 `identified_item_count = 0`，系统各页面如何解释？**
   - **数据库事实核查**：该订单共有 6 组商品明细（合计 `sample_count = 50`），关联 3 个入仓包裹（`SF5001` 实收 20 件、`SF5002` 实收 18 件、`SF5003` 实收 10 件，包裹级扫码实收合计 `48` 件，少到 `2` 件），因此系统自动触发了收货差异工单 `TK-4FC7B23787`。由于仓库在发现少件差异后暂停了后续逐件拆包贴码建档，`warehouse_items` 表中该订单已建档核身实物数为 `0`。
   - **本轮展示修复**：在 `/admin/orders` 与 `/admin/orders/QW-63A714CB655E` 中，将原本混淆的数量拆解为 **6 个明确维度**：`委托 50 件 (6 组 SKU)`、`预报包裹 3 个 (到仓 3)`、`实收 48`、`核身 0`、`已检 0`、`少到 2 件`，同时在“下一步责任方”列显式标注 **`仓库拆包建档岗（尚有 48 件已收包裹待拆包核身）`**，使运营人员一眼看清“包裹已收 48 件但尚未逐件贴码建档”的真实阶段。
2. **质疑点 8.2：实物 `S-F53EFBDD` 状态为 `outbound / pending`、`DSP-E1BB0631` 状态为 `disposed / pending`，为何已出库/已处置还是 `pending`？**
   - **数据库事实核查**：`warehouse_items` 表有两个独立状态列：`custody_state`（物理在库状态）和 `identity_state`（订单 SKU 核身状态）。`S-F53EFBDD` 是未绑单无主包裹直接原样退回出库（`order_id IS NULL, custody_state = 'outbound', identity_state = 'pending'`）；`DSP-E1BB0631` 是逾期未认领实物经双人审批直接销毁处置（`custody_state = 'disposed', identity_state = 'pending'`）。它们从未进入“核对客户订单 SKU 明细”环节，因此 `identity_state` 保持默认值 `pending`。
   - **本轮展示修复**：通过 `WarehouseItemLifecycleTags` 组件对 `custody_state ∈ {outbound, disposed}` 且 `identity_state = pending` 的实物，渲染为 **`已出库 / 未绑单原样退回/出库（免 SKU 核身）`** 与 **`已处置 / 逾期/无主直接处置（免 SKU 核身）`**，彻底消除“已销毁却待核身”的字面矛盾。
3. **质疑点 8.3：客户 `p0-1d119726...` 存在 `30` 个未结工单，是真实积压还是测试夹具产物？**
   - **数据库事实核查**：查询 `support_tickets` 表发现，系统共有 `41` 个未结工单，其中 `30` 个归属测试账号 `p0-1d119726-c192-486b-b06a-c0962a84056c@qcw.test`，由集成测试反复执行大批量收货差异用例生成。
   - **本轮展示修复**：在 `/admin/customers` 与 `/admin/tickets` 中保留真实工单计数，同时在 `/admin` 运营总览明确区分 `正式业务单口径 (5 笔)` 与 `隔离测试单口径 (122 笔)`，并在客户档案支持按风险与测试账号检索过滤。
4. **质疑点 8.4：运单 `SF17761588058290` 承运商状态 `delivered`，包裹状态 `received`，但 `weight_g` 为空且 `warehouse_item_count = 0`，物流监控如何暴露此断点？**
   - **数据库事实核查**：该运单包裹已完成到仓扫码（`packages.state = 'received'`），但收货员尚未录入实测重量（`weight_g IS NULL`），也尚未执行拆包建档（`warehouse_items` 为 0）。
   - **本轮展示修复**：在 `/admin/logistics` 的全宽工作台 `#waybill-detail-workbench` 顶部新增 **4 阶段状态对照条**，对该运单清晰展示：`① 承运商运输与签收：已签收` → `② 仓库物理扫码实收：已扫码入仓` → `③ 包裹实测称重：未称重（黄色预警）` → `④ 拆包建档与 SKU 核身：0 件已建档（待拆包核身预警）`。
5. **质疑点 8.5：库位 `R-01`（收货暂存区）堆放了 `65` 件实物，是否存在积压风险？**
   - **数据库事实核查**：`R-01` 容量上限为 `200`，当前存放 `65` 件已收货待上架/待质检实物（占比 `32.5%`），是全仓实物最集中的暂存区。
   - **本轮展示修复**：在 `/admin/storage/locations` 顶部新增 **库位容量与收货暂存区积压实时监控横幅**，当 `R-01` 暂存区实物超过阈值或存在异常隔离件（`Q-01`）时自动置顶预警，并支持一键展开 `R-01` 全宽实物清单逐件核查。
6. **质疑点 8.6：法务协议 `privacy / report_notice / restricted_items` 的生效版本 `demo-v1` 内容为 `"Development fixture. Use test parcels and simulated payments only."`**
   - **核查与修复**：属实。已在 `/admin/legal` 置顶展示 **P0 生产合规风险告警横幅**，在列表标注红色 `开发夹具文本 (Demo Fixture)` 标签与历史签署人次，并提供全宽正文预览工作台与新正式版本发布表单，同时在 §11.11 列为生产上线前必换项。
7. **质疑点 8.7：库存事故 `INC-20260329-52C1DC` 审计日志显示原始 JSON 且含未映射动作 `print_label / verify_label_readback`**
   - **核查与修复**：属实。已在 `app/admin-labels.tsx` 补齐 `print_label（打印面单）`、`verify_label_readback（面单回读校验）` 等全部动作中文映射，并通过 `formatAuditSnapshotSummary` 将审计快照转换为易读的中文业务字段摘要。
8. **质疑点 8.8：运营总览卡片数字与点击进入的列表数字不一致**
   - **核查与修复**：属实（正式单 vs 含测试单全量口径混用）。已通过总览双口径切换器与 URL 参数联动彻底解决，两套口径下卡片数字与目标队列 100% 对齐。
