## B. 跨系统业务关联与真实后端缺陷修复清单

1. **退款执行后原支付状态自动同步（`packages/core/payments.ts`）**：
   - 新增 `syncPaymentRefundState(db, paymentId)`，在 `executeRefund` 及 Stripe Webhook（`refund.created` / `refund.updated`）确认退款成功后，汇总该支付单下全部 `state = 'succeeded'` 的退款总额：
     - 当 `0 < succeeded_refunds < payment.amount_cents` 时，自动将 `payments.state` 更新为 `'partially_refunded'`（部分退款）；
     - 当 `succeeded_refunds >= payment.amount_cents` 时，自动将 `payments.state` 更新为 `'refunded'`（已全额退款）。
2. **退款独立驳回工作流与可退余额释放（`packages/core/payments.ts` & `packages/core/http.ts`）**：
   - 新增 `refundReject(db, actor, id, rev, reason, sessionHash)` 及路由 `POST /staff/admin/refunds/:id/reject`（兼容 `POST /staff/refunds/:id/reject`）：
     - 强制校验 `super_admin` 角色、最近 15 分钟员工 MFA 会话、组织级并发锁、乐观锁版本号 `revision` 及职责分离 SoD（`requested_by !== actor.id`）；
     - 将退款状态置为 `'rejected'`，自动释放此前占用的可退余额（`refundable_cents`），并写入不可变审计事件 `reject_refund`。
   - 扩展 `refundApprove` 及 `POST /staff/admin/refunds/:id/approve` 支持传入可选审批备注 `reason` / `note` 并落库至 `approve_refund` 审计记录，同时保持原 OpenAPI `POST /staff/refunds/{id}/approve` 严格契约不变。
3. **新增 Admin 聚合读取与详情服务层（`packages/core/admin-reads.ts` & `packages/core/http.ts`）**：
   - 新增并挂载 11 个专用后台端点：
     - `GET /staff/admin/payments`、`GET /staff/admin/payments/:id`
     - `GET /staff/admin/refunds`、`GET /staff/admin/refunds/:id`
     - `GET /staff/admin/customers`、`GET /staff/admin/customers/:id`
     - `GET /staff/admin/inspections`
     - `GET /staff/admin/dispositions-overview`
     - `GET /staff/admin/incidents/:id`
     - `GET /staff/admin/disposals/:id`
     - `GET /staff/admin/storage/locations/:id`
4. **增强既有订单、工单、物流与审计查询（保持 100% 既有契约与隐私红线）**：
   - `packages/core/reads.ts`：
     - `adminDesk` 补充 10 项待办计数与 `unmatchedPackages`（含 `revision`、`location_code` 与 `outer_photo_ids`）；
     - `searchStaffOrders` 补充客户收件码 `receiving_code`、服务/品类、SKU 组数、期望/实收/核身件数、质检进度、付款状态、阻塞与工单计数，同时严格遵守不返回客户邮箱的隐私断言；
     - `staffOrderDetail` 补充 `expected_lines_summary`、`tasks`、`reports`、`quotes`、`charges`、`payments`、`refunds`、`dispositions`，并严格保留 `shipments` 不暴露 `destination_snapshot` 的安全红线。
   - `packages/core/tickets.ts`：工单队列与详情补充客户收件码、优先级、最新消息摘要、关联支付单 ID 与事件操作人姓名。
   - `packages/core/logistics.ts`：运单监控、异常告警与签收未实收队列补充客户收件码、客户 ID、关联订单号、包裹码与承运商中文名。
   - `packages/core/audit-read.ts`：补充操作人姓名、角色列表、客户收件码、关联订单号与可读对象标识，同时严格保留 `before`/`after` 投影且不暴露 `ip`/`meta`。
5. **前后端联调与测试中发现并即时修复的 7 项真实缺陷**：
   - 修复客户详情页更新账号状态路径为 `/staff/users/:id/status`，并支持 `active` / `restricted` / `disabled` 三态审计切换；
   - 修复包裹认领申诉裁决路径为 `/staff/intake-claims/:id/decision`（参数 `{ decision, reason }`）及外箱照片前置校验；
   - 修复无主包裹人工绑定客户（`POST /staff/packages/:id/bind-owner`）凭证要求：必须上传全新 `label_photo` 凭证并携带包裹 `revision`，将原表格行内拥挤表单迁入独立 `ModalDrawer`，根除 `<input type="file">` 遮挡提交按钮的布局缺陷；

## C. 三级业务操作体系与权限、SoD、MFA、幂等守卫

1. **三级操作体系落地**：
   - **第一级（工作队列与列表）**：提供多维状态选项卡、精确检索、环境隔离（正式单 vs 测试单）、可读业务编号（`QW-...`、`QCW-...`、`PAY-...`、`RFD-...`、`DSP-...`、`P-...`、`S-...`）、异常徽标与下一步操作入口。
   - **第二级（独立详情工作台）**：订单（7 分组）、客户（360 档案）、支付（6 分区）、退款（资金公式 + 履约背景）、事故（实物 + 证据 + 赔付全链）、特殊处置（双人审批 + 实物清单）均具备独立 URL 路由，支持刷新恢复、深链分享与服务端鉴权。
   - **第三级（受控执行与审批）**：所有高风险写操作均展示前置条件与业务影响，执行乐观锁 `revision` 校验、`Idempotency-Key` 幂等保护、审计原因必填及即时状态反馈。
2. **角色权限（RBAC）与职责分离（SoD）矩阵**：
   - 保持 `staffTabs("admin", ["finance" | "support" | "template_admin"])` 既有导航契约 100% 兼容，同时通过 `canOpenStaffPage` 与页内子导航支持角色按授权访问对应详情工作台；
   - **退款审批/驳回 SoD**：`requested_by !== actor.id`，且须 `super_admin` + 15 分钟内 MFA 验证；
   - **库存事故赔偿审批 SoD**：`proposed_by !== actor.id`，且非财务角色（如 `receiver`）访问 `/staff/admin/incidents/:id` 时自动隐藏赔偿金额（`financial_restricted: true`）；
   - **客户隐私裁剪**：`/staff/orders` 列表绝不暴露客户邮箱；`finance` 角色访问客户 360 详情与支付详情时邮箱自动掩码（`c***@qcw.test`）；`customer` 与 `receiver` 访问财务/客户管理 API 严格返回 `403 FORBIDDEN`。
